# GSD 开发流程问答纪要（会话整理）

**整理日期：** 2026-04-10  
**范围：** 同一会话中关于 GSD（Get Shit Done）工作方式、命令分工、与仓库协作规则的问答与结论。  
**说明：** 本文是**对话摘要**，不替代官方 `help` 工作流；命令行为以 `.codex/get-shit-done/workflows/*.md` 为准。

---

## 1. 背景（本会话里实际发生的事）

- 仓库**已存在** `.planning/`（`project_exists: true`），不宜重复执行完整的 `/gsd-new-project` 从零初始化。
- 温度预测页需求通过 **`/gsd-add-phase`** 拆成阶段，并曾出现 **「未充分对齐就先改代码」** 的摩擦；后续用 **`/gsd-discuss-phase`**、补 **`03-CONTEXT.md`** 等方式把账本对齐。
- 用户希望把 **「问了什么 / 答了什么」** 固化成文档，便于以后查阅。

---

## 2. 问答汇总

### Q1：`/gsd-new-project` 我想用来做页面优化，为什么说不适合整段重跑？

**答：**  
`init new-project` 若返回 **`project_exists: true`**，按 GSD 设计应走 **`/gsd-progress`** 或在当前里程碑下 **加阶段 / 更新需求**，而不是再次从零 `new-project`。  
页面级优化更适合作为 **棕地增量**：`REQUIREMENTS` + `ROADMAP` + `add-phase`，而不是重建整个规划树。

---

### Q2：`/gsd-add-phase` 会不会自带「讨论 / 对齐」？为什么加完阶段又直接去改代码会让人不舒服？

**答：**  

- **`/gsd-add-phase` 只做「占坑」**：算阶段号、建阶段目录、改 `ROADMAP.md`、更新 `STATE` 等（见 `workflows/add-phase.md`）。**不包含**需求讨论、不写 `CONTEXT.md`。
- **讨论 / 对齐** 对应 **`/gsd-discuss-phase <N>`**，产出通常是 **`NN-CONTEXT.md`**（+讨论日志）。
- 若团队规则要求 **产品行为变更前先 Mini Align**，则应在 **同一轮里避免**「add-phase + 大面积改代码」而不经过 discuss 或明确豁免（例如用户说「直接做」）。

---

### Q3：GSD「正确」的开发流程大概是什么？

**答（最小可执行顺序）：**

1. 新项目且未初始化：`/gsd-new-project`（已初始化则跳过）。
2. 新工作包：`/gsd-add-phase <简述>`。
3. 阶段开工前（推荐）：`/gsd-discuss-phase N` → 产出 `N-CONTEXT.md`。
4. 拆任务：`/gsd-plan-phase N` → 产出 `PLAN.md` 等。
5. 实现与收尾：`/gsd-execute-phase N`（或小改用 `/gsd-quick`，视项目约定）。
6. 与仓库 **`.cursor/rules/project-zh.mdc`** 一致：涉及产品行为 / 多文件时，**先对齐再实现**，除非用户明确豁免。

**记忆口诀：** `add-phase`（占坑）→ `discuss-phase`（定 CONTEXT）→ `plan-phase`（拆任务）→ 实现与验证。

---

### Q4：GSD 里有没有「总指导文档 / 总入口」，不用一个一个 skill 手动点？

**答：**  

- **命令参考（说明书）**：`/gsd-help` → 输出来自 `.codex/get-shit-done/workflows/help.md` 的 **GSD Command Reference**。
- **不知道用哪条命令**：`/gsd-do` + 自然语言描述意图 → 路由到合适的 `/gsd-*`（本身不代替执行）。
- **懒得想下一步**：`/gsd-next` → 读 `STATE.md`、`ROADMAP.md`、阶段目录等，**推断**下一步（如缺 `CONTEXT` 则建议 `discuss-phase`）。
- **没有**单一 skill 永久替代所有步骤：设计上是模块化；**自动串联**依赖命令上的 **`--auto` / `--chain`** 或配置里的 **`workflow.auto_advance`** 等（见各 `workflows/*.md`）。

---

### Q5：跑 `/gsd-next` 时，当前仓库「下一步」可能是什么？

**答（本会话中的实例）：**  

- Phase 3 目录里**没有** `*-CONTEXT.md` 时，按 `workflows/next.md` 的 **Route 2**，下一步多为 **`/gsd-discuss-phase 3`**。  
- 补完 `03-CONTEXT.md` 后，下一步通常变为 **`/gsd-plan-phase 3`**（有 CONTEXT、尚无 PLAN 时）。  
- **注意：** 若更早阶段有 CONTEXT 但从未 `plan-phase`，机器状态可能仍显示「计划数为 0」；棕地项目常需 **人工 + STATE** 对齐「当前焦点阶段」。

---

### Q6：任务做完以后，GSD 会不会自己触发下一步？

**答：**  

- **默认不会。** GSD 一般不会在「你提交代码 / 关掉任务」时后台自动跑命令。
- **自动推进** 出现在：某次命令带了 **`--auto` / `--chain`**，或配置打开 **`workflow.auto_advance`** 等，使**同一会话链路**里继续调用下一阶段。
- 日常做法：阶段性手动 **`/gsd-next`** 或显式 **`/gsd-plan-phase` / `/gsd-execute-phase`**，并维护 `STATE.md`。

---

### Q7（实践）：`03-CONTEXT.md` 是怎么补上的？

**答：**  
在用户确认「好的开始」后，根据 `ALIGNMENT.md`、已实现代码与需求 **补写** `03-CONTEXT.md` 与 `03-DISCUSSION-LOG.md`，使 **`/gsd-next` 能进入 plan 阶段**；并在 `STATE.md` 留痕。  
这属于 **「实现先行、文档追溯」** 的补录，理想情况仍是 **先 discuss 再实现**。

---

### Q8：GSD 有没有「归档」？两个 Phase 做完想归档怎么办？

**答：**  

- **有，但分粒度：**  
  - **里程碑级（重）**：`/gsd-complete-milestone` — 在 `.planning/milestones/` 生成版本化快照（ROADMAP/REQUIREMENTS 等），可选迁移阶段目录。  
  - **阶段目录整理**：`/gsd-cleanup` — 将已完成里程碑下的 `phases` 迁入 `milestones/vX.Y-phases/`。  
  - **轻量归档**：在 `zzz-docs/归档/` 等写交付纪要，**不**替代上述命令，适合答辩/交接速览。  
- **未跑** `complete-milestone` 时，也可在 **`ROADMAP.md` / `STATE.md`** 手工标注阶段「已交付」，与轻量 md 并行。

---

### Q9：完成一个 Phase 之后，怎么让 GSD 更新 `PROJECT.md`、`REQUIREMENTS.md`、`STATE.md`？有专门命令吗？

**答：**  

- **没有三条独立命令**分别只改这三份文件；**正规收口**是走 **`/gsd-execute-phase <N>`** 全流程，在验证通过、阶段标记完成时，工作流会调用 **`gsd-tools phase complete`**，由 CLI 更新 **`ROADMAP.md`、`STATE.md`、`REQUIREMENTS.md`（含追溯）** 等。  
- 另一步会 **演进 `PROJECT.md`**（例如将本阶段已验证需求从 Active → Validated，更新 Last updated），见 `workflows/execute-phase.md` 中 `update_project_md`。  
- **前提**：阶段通常需有 **`PLAN.md`** 且按计划执行完毕；若「先写代码后补 GSD」，可补 **`/gsd-plan-phase N`** 再 **`/gsd-execute-phase N`**，或按 `PROJECT.md` 的 **Evolution** 约定 **手工**同步三文档。  
- **内部**有 `transition.md`，**没有**用户级 `/gsd-transition`，由 `execute-phase` 等在合适时机触发。  
- **`/gsd-verify-work`** 为对话式 UAT，**不**等同于自动 `phase complete`。
