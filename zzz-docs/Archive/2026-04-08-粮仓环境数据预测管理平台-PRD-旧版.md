## 1. Executive Summary

### Problem Statement

当前粮仓管理仍较依赖人工巡检和经验判断，环境数据分散、历史记录难追溯、趋势风险难提前识别。仅靠实时温湿度查看，无法有效支撑粮仓环境的规范化管理和短期预警决策。

### Proposed Solution

建设一个基于 Spring Boot 的粮仓环境数据预测管理平台，统一管理粮仓基础信息、环境监测数据和温度趋势预测结果，并通过可视化页面为管理人员提供查询、分析和辅助决策能力。

### Success Criteria

- 系统可完成用户登录、仓库管理、环境数据管理、数据展示、温度预测 5 个核心模块。
- 系统支持按仓库、指标、时间范围查询历史环境数据。
- 系统可对温度数据输出未来短期预测结果，并以列表或图表展示。
- 系统可在本地稳定演示，主要业务流程可完整走通。
- 页面和接口结构清晰，符合本科毕业设计“可运行、可演示、可说明”的要求。

## 2. User Experience & Functionality

### User Personas

#### 2.1 系统管理员

- 负责系统用户维护、仓库档案维护、平台整体配置。
- 关注系统是否完整、数据是否规范、页面是否可用。

#### 2.2 仓库管理员

- 负责查看本仓库环境数据、录入数据、查看趋势和预测结果。
- 关注某个粮仓当前状态是否异常，后续是否有升温风险。

#### 2.3 查看者

- 仅查看图表、统计概览和预测结果。
- 适用于演示、汇报或领导查看场景。

### User Stories

#### Story 1: 登录与身份区分

As a 用户, I want to 登录系统并看到与自己身份匹配的页面入口 so that 我可以进入对应功能模块。

Acceptance Criteria

- 提供登录页。
- 登录成功后进入系统首页。
- 页面可展示当前用户名称和角色。
- 至少区分 `ADMIN`、`WAREHOUSE_MANAGER`、`VIEWER` 三类角色。

#### Story 2: 仓库信息管理

As a 管理员, I want to 维护仓库基础信息 so that 平台中的环境数据能够正确关联到具体粮仓。

Acceptance Criteria

- 支持查看仓库列表。
- 支持新增、编辑仓库基础信息。
- 仓库信息至少包含编号、名称、位置、容量、负责人、状态。
- 列表页面支持按名称或状态筛选。

#### Story 3: 环境数据录入与存储

As a 仓库管理员, I want to 录入或导入环境数据 so that 系统能够形成可追溯的历史记录。

Acceptance Criteria

- 支持录入温度、湿度等基础环境指标。
- 每条数据至少包含仓库、指标类型、指标值、采集时间。
- 数据按时间顺序存储。
- 后续查询可基于历史数据回溯。

#### Story 4: 环境数据查询与可视化

As a 用户, I want to 通过图表和表格查看历史环境数据 so that 我能快速理解粮仓环境变化趋势。

Acceptance Criteria

- 支持按仓库筛选数据。
- 支持按指标类型筛选数据。
- 支持按时间范围筛选数据。
- 支持表格展示。
- 支持折线图或柱状图展示。

#### Story 5: 温度趋势预测

As a 仓库管理员, I want to 查看未来短期温度预测结果 so that 我可以提前发现潜在风险。

Acceptance Criteria

- 支持选择仓库和预测步数。
- 基于历史温度数据生成未来若干时间点的预测值。
- 预测结果至少以表格或图表方式展示。
- 当历史样本不足时，系统能给出明确提示。

#### Story 6: 仪表盘概览

As a 用户, I want to 在首页快速看到仓库总览、预警摘要和关键指标 so that 我不用逐页查找信息。

Acceptance Criteria

- 首页展示仓库数量、今日采样量、预警数量等核心统计。
- 首页展示最新预警或重点关注事项。
- 首页展示最近的预测摘要或关键监测信息。

### Non-Goals

- 不建设真实物联网设备接入链路。
- 不实现 LoRa、5G、GSM 等通信层。
- 不实现机器人巡检、路径规划、数字孪生、区块链。
- 不追求复杂深度学习模型或高精度 AI 预测。
- 不做生产级部署、运维平台和多租户系统。

## 3. AI System Requirements

本项目不属于复杂 AI 系统。

### Tool Requirements

- 无强制 AI 工具要求。
- 预测模块可采用简单线性回归、滑动平均或加权移动平均。

### Evaluation Strategy

- 以“结果可解释、页面可展示、逻辑可说明”为主。
- 不以学术级预测精度作为主要交付目标。
- 重点验证：是否能根据历史温度数据给出合理的短期趋势结果。

## 4. Technical Specifications

### Architecture Overview

基于开题报告，本项目采用前后端分离架构：

- 前端：负责登录页、仪表盘、仓库管理、环境数据查询、预测展示。
- 后端：负责用户、仓库、环境数据、预测逻辑等 RESTful 接口。
- 数据库：负责存储用户、仓库、环境数据和预测记录。

核心数据流：

1. 用户登录系统。
2. 用户查看仓库信息与环境数据。
3. 系统按查询条件读取历史数据。
4. 后端调用轻量预测逻辑生成预测结果。
5. 前端使用图表和表格展示数据与预测结果。

### Integration Points

#### 4.1 前端

- 开题报告原始技术路线：`Vue.js + ECharts`
- 当前静态演示版：`Next.js + Ant Design + mock`

#### 4.2 后端

- `Spring Boot`
- `MyBatis`
- `RESTful API`

#### 4.3 数据库

- `MySQL`

建议表结构：

- `sys_user`
- `sys_role`
- `sys_user_role`
- `warehouse`
- `sensor_metric`
- `sensor_data`
- `prediction_record`

#### 4.4 核心接口

- `POST /api/auth/login`
- `GET /api/dashboard/overview`
- `GET /api/warehouses`
- `POST /api/warehouses`
- `GET /api/sensor-data`
- `POST /api/sensor-data`
- `POST /api/predictions/temperature`

### Security & Privacy

- 演示阶段仅需基础登录能力。
- 角色权限按页面和功能按钮进行基础区分。
- 正式实现时密码应加密存储，演示阶段可简化。
- 数据主要为环境监测数据，不涉及高敏感个人隐私，但仍应避免明文暴露用户密码。

## 5. Risks & Roadmap

### Phased Rollout

#### MVP

- 登录页
- 仪表盘
- 仓库管理
- 环境数据录入与查询
- 图表展示
- 温度预测展示
- 本地运行与演示

#### v1.1

- Excel 导入环境数据
- 更完整的角色权限控制
- 预测结果记录留存
- 更多筛选条件和异常提示

#### v2.0

- 对接真实传感器数据源
- 支持更多环境指标
- 异常预警规则引擎
- 移动端或大屏展示

### Technical Risks

#### 风险 1：开题报告范围与实现范围不一致

- 开题报告中包含较多“技术趋势”描述，如数字孪生、机器人、区块链。
- 如果不做范围收敛，容易把毕业设计做得过大。

应对方式

- 以“平台管理 + 环境数据 + 温度预测 + 可视化”为主交付范围。

#### 风险 2：预测算法实现过重

- 若过早引入复杂机器学习框架，会显著增加实现和答辩成本。

应对方式

- 采用轻量、可解释的预测算法。

#### 风险 3：缺少真实数据源

- 若没有传感器接入，系统展示可能较空。

应对方式

- 先使用 mock 数据或模拟数据。
- 保证页面和流程完整，满足毕业设计演示要求。

#### 风险 4：时间不足导致模块不完整

- 如果同时做过多高级功能，可能影响整体交付质量。

应对方式

- 优先确保 MVP 完整可运行。
- 将扩展能力放入后续版本规划。

## 附：结合开题报告的最终产品定义

从开题报告分析，这个项目最终不是“完整智能粮仓硬件系统”，而是一个面向粮仓管理场景的软件平台。它最后应当具备以下结果：

- 能管理粮仓基础信息。
- 能存储和查询温度、湿度等环境数据。
- 能用图表展示历史数据变化趋势。
- 能对温度进行短期预测。
- 能给管理人员提供基础辅助决策能力。
- 能以一个完整的 Web 平台形式进行毕业设计演示和答辩说明。

换句话说，最终成果应是一个“可登录、可管理、可查询、可展示、可预测”的粮仓环境数据管理平台，而不是重硬件、重算法、重工业控制的大型系统。
