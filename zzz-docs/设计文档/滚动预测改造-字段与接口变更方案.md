# 滚动预测改造字段与接口变更方案

## 1. 文档目的

本文档用于承接“旧多指标短期预测实现”和“新粮温滚动预测闭环设计”之间的差异，回答三个问题：

- 现有系统哪些结构可以保留
- 哪些字段和表必须调整
- 接口应该如何从旧口径迁移到新口径

本文档面向后续的 `schema.sql` 修改、后端接口改造和前端页面重写。

## 2. 当前旧模型与新模型的核心差异

| 维度 | 当前旧模型 | 新模型 |
| --- | --- | --- |
| 预测重点 | 多指标独立短期预测 | 粮温滚动预测闭环 |
| 时间粒度 | 未来若干步，偏短期 | 按天预测，按月滚动组织 |
| 训练信息 | 仅隐含在历史样本里 | 明确记录训练参考区间 |
| 修正机制 | 无正式版本链 | 新真实数据回填后生成新一轮预测 |
| 温度数据结构 | `sensor_data` 单值时序 | 测点定义 + 原始记录 + 汇总分析 |
| 预警 | 任务级风险等级 | 真实预警 + 预测预警 |

## 3. 表级变更建议

### 3.1 可保留表

- `warehouse`
- `sys_user`
- `sys_role`
- `sys_user_role`
- `sensor_metric`

原因：

- 这些表仍符合当前业务范围，不需要推翻。

### 3.2 保留但降级用途的表

#### `sensor_data`

变更后用途：

- 主要用于湿度、二氧化碳等普通单值环境数据
- 不再作为粮温主真相源

原因：

- 粮温报表是多测点矩阵，继续放在单值表里会丢失结构

### 3.3 需要新增的表

#### `grain_temp_point`

作用：

- 保存粮温测点定义

关键新增字段：

- `warehouse_id`：所属仓库
- `probe_code`：测温缆编号
- `zone_code`：区域编号
- `layer_no`：层号
- `point_no`：点位号
- `point_name`：测点名称

#### `grain_temp_record`

作用：

- 保存粮温原始测点记录

关键新增字段：

- `warehouse_id`：所属仓库
- `point_id`：测点 ID
- `collected_at`：检测时间
- `temperature_value`：温度值
- `batch_no`：批次号

#### `grain_temp_summary`

作用：

- 保存系统自动生成的层温与整仓汇总结果

关键新增字段：

- `avg_temp`：整仓平均温度
- `max_temp`：最高温
- `min_temp`：最低温
- `layer_1_avg` ~ `layer_4_avg`：层平均温度
- `warning_level`：真实预警等级
- `warning_flag`：是否预警
- `warning_message`：预警说明

### 3.4 需要改造的表

#### `prediction_task`

旧字段保留：

- `task_no`
- `warehouse_id`
- `metric_code`
- `algorithm_code`
- `algorithm_name`
- `sample_size`
- `status`
- `risk_level`
- `requested_by`
- `requested_at`
- `completed_at`
- `summary`

旧字段调整：

- `future_steps`
  - 旧含义：简单未来步数
  - 新建议：逐步废弃，用更明确的预测窗口字段替代

新增字段：

- `parent_task_id`：父任务 ID
- `task_round`：预测轮次
- `data_source_type`：数据来源类型
- `target_type`：预测目标类型
- `train_start_time`：训练开始时间
- `train_end_time`：训练结束时间
- `forecast_start_time`：预测开始时间
- `forecast_end_time`：预测结束时间
- `based_on_actual_end_time`：已纳入真实数据截止时间
- `forecast_days`：预测天数
- `trigger_type`：触发类型
- `adjust_status`：修正状态

#### `prediction_result`

旧字段保留：

- `task_id`
- `actual_value`
- `predicted_value`

旧字段调整：

- `predicted_time`
  - 建议重命名或语义升级为 `result_time`

- `step_index`
  - 从“未来步数序号”升级为“本轮预测中的每日序号”

新增字段：

- `phase_type`：结果阶段类型
- `error_value`：误差值
- `error_rate`：误差率
- `warning_level`：预测预警等级
- `warning_flag`：是否预警
- `warning_message`：预警说明
- `is_corrected`：是否属于修正结果

## 4. 接口级变更建议

### 4.1 可继续复用的接口

- `POST /api/auth/login`
- `GET /api/warehouses`
- `POST /api/warehouses`
- `GET /api/metrics/options`

### 4.2 需要改造的接口

#### 旧：`POST /api/predictions`

旧职责：

- 选择仓库、指标、未来步数后直接预测未来结果

新职责建议：

- 选择仓库
- 选择预测对象，如整仓平均温度或某层平均温度
- 指定训练参考区间
- 指定未来预测窗口
- 创建一轮预测任务并返回结果

建议请求字段升级为：

- `warehouseId`
- `metricCode`
- `targetType`
- `trainStartTime`
- `trainEndTime`
- `forecastStartTime`
- `forecastEndTime`
- `algorithmCode`

#### 旧：`POST /api/sensor-data/import`

旧职责：

- 导入普通环境数据 CSV/XLS/XLSX

新职责建议拆分：

1. 普通环境数据导入接口
2. 粮温 XLS 导入接口

### 4.3 需要新增的接口

#### `POST /api/grain-temp/import`

作用：

- 导入固定模板粮温 XLS
- 解析上半部分测点矩阵
- 入库原始测点数据
- 自动生成汇总分析

#### `GET /api/grain-temp/records`

作用：

- 查询粮温原始测点数据

#### `GET /api/grain-temp/summaries`

作用：

- 查询粮温汇总分析结果

#### `POST /api/predictions/{taskId}/correct`

作用：

- 读取新增真实数据
- 回填旧预测真实值
- 计算误差
- 生成新一轮修正预测

#### `GET /api/predictions/tasks`

作用：

- 继续保留，但返回需要补充：
  - `taskRound`
  - `parentTaskId`
  - `triggerType`
  - `adjustStatus`
  - `forecastStartTime`
  - `forecastEndTime`

#### `GET /api/predictions/tasks/{taskId}`

作用：

- 返回任务详情和每日结果
- 包含真实值、预测值、误差和预警信息

## 5. 前端改造方向

### 5.1 现有可保留部分

- 登录页
- 仓库管理页
- 用户管理页基础框架
- API 层封装方式
- 仪表盘整体布局

### 5.2 需要重写或大改的部分

#### `DataView.vue`

改造重点：

- 新增粮温 XLS 导入入口
- 区分普通环境数据与粮温数据

#### `PredictionView.vue`

改造重点：

- 从“多指标短期预测”切换为“滚动预测闭环”
- 展示训练区间、预测区间、修正轮次
- 展示真实值、预测值、误差与高温预警

#### `grain.js`

改造重点：

- 调整预测接口请求结构
- 增加粮温导入与查询 API
- 增加修正预测 API

## 6. 推荐改造顺序

1. 先更新真相源和 `.explore/`
2. 再改 `schema.sql`
3. 再改后端实体、Mapper、Service、Controller
4. 最后改前端页面与 API 适配层

## 7. 最终结论

当前项目不是简单“在旧代码上补几个字段”，而是需要一次明确的模型切换：

- 旧路线：多指标独立短期预测
- 新路线：粮温滚动预测闭环

因此后续最稳的做法是：

- 先以本文件和新版 PRD / 数据库设计为真相源
- 再分阶段重构 `schema.sql`、后端接口和前端预测页
- 必要时接受“局部重写”，不要被旧页面和旧 DTO 绑定
