# 决策日志

## 2026-03-25 决策：前端直接调用本地 HTTP 后端
- **背景**：需要尽快让前后端形成稳定、低耦合的最小对话链路。
- **选择**：前端通过 `fetch` 请求本地 Python `FastAPI` 服务，而不是走 Electron 主进程桥接。
- **原因**：接口清晰、调试方便、后续扩展记忆和上下文接口也更顺滑。
- **影响**：后端密钥只保留在 Python 侧，前端只处理业务响应与错误提示。

## 2026-03-26 决策：先冻结事件协议骨架，优先转入记忆 MVP
- **背景**：`bubble.show`、`emotion.set`、`motion.play`、`mode.switch`、`move.intent` 的基础协议与前端消费链路已经打通。
- **选择**：当前不继续扩张事件种类，先把主要后端工作重心转向 `Task 7` 的记忆服务 MVP。
- **原因**：事件协议已满足当前演示与最小控制需求，继续扩协议的收益低于完善可持久化记忆。
- **影响**：后续设置页、上下文感知和答辩演示将依赖更稳定的记忆接口推进，减少返工。

## 2026-03-26 决策：记忆模块按低耦合可替换架构推进
- **背景**：用户已明确后期很可能更换记忆底层实现，当前 `MemoryStore -> InMemoryStore` 的抽象基础还不够支撑低成本替换。
- **选择**：后续记忆模块采用 `ChatOrchestrator -> MemoryService -> MemoryPolicy + MemoryStore` 的分层结构，并通过 provider factory 选择 `in_memory`、`sqlite` 或其他实现。
- **原因**：这样可以把聊天编排、记忆策略和底层存储解耦，避免未来切换 SQLite、向量库或外部服务时改动聊天主链路。
- **影响**：`Task 7` 可以先交付 SQLite MVP，但不得把具体 provider 细节写死到 `ChatOrchestrator` 或聊天路由中；`Task 12` 将继续升级 schema、策略与更复杂的替换能力。

## 2026-03-26 决策：模型切换按钮显式化，拖拽换模仅作用于正比模型
- **背景**：当前已经接入正比模型和 `QQ小黑猫` 两套模型，用户希望 toolbar 上有一个明确的 Q版切换按钮，并要求拖拽换模只在正比模型下生效。
- **选择**：toolbar 使用明确的 `Q版` 按钮切换常驻模型类型；当常驻模型为正比时，拖拽中临时切换到 `QQ小黑猫`，拖拽结束后恢复；当常驻模型本身已是 Q版时，拖拽中不做临时换模。
- **原因**：把“常驻模型切换”和“拖拽态临时换模”分离后，交互规则更清楚，也便于后续把模型类型接入设置页。
- **影响**：前端需要同时维护常驻模型类型和拖拽态显示模型；后续如需模型持久化，应在设置页或本地配置层处理，而不是把状态散落在拖拽逻辑中。

## 2026-03-26 决策：后端继续沿服务边界演进，优先扩展性而非框架绑定
- **背景**：当前后端已经具备 `ChatOrchestrator`、`LlmService`、`MemoryService` 和可替换 `MemoryStore` 的基础结构，用户希望后续可外接更强记忆方案，并预留接 LangChain 类框架或 agent 能力的空间。
- **选择**：继续保持 `ChatOrchestrator` 精简，把新增能力拆到独立服务边界，例如未来的 `ContextService`、`AgentService` 或工具注册层，而不是直接把第三方框架逻辑写进聊天主链路。
- **原因**：这样能最大限度降低对现有闭环的冲击，也便于后续按需接入向量库、外部记忆、工具执行和多步规划。
- **影响**：当前后端被明确定位为“可扩展对话底座”，不是已经完成的完整 agent runtime；后续扩展要继续遵守低耦合原则。

## 2026-03-26 决策：Task 8 的上下文感知先落 Windows 活动窗口 MVP
- **背景**：需要尽快完成轻量上下文感知，但同时必须遵守“失败不影响聊天”和“系统提示明确说明来源”的验收要求。
- **选择**：新增独立 `ContextService` 和 Windows 活动窗口 provider，当前只采集活动应用名与窗口标题，并通过 context status / runtime toggle API 暴露控制面。
- **原因**：这是当前阶段最小、最容易解释且隐私风险最低的上下文信号，同时也能保住低耦合服务边界。
- **影响**：聊天主链路现在可以按需注入上下文来源说明；未来若要扩更多 provider，可继续沿 `ContextProvider` 边界扩展，而不用回改 `ChatOrchestrator`。

## 2026-03-26 决策：新增 `/dev/memory` 作为记忆联调与观察入口
- **背景**：当前 MVP 记忆已经能写入和召回，但开发时缺少一个直接查看数据库中记忆记录的入口。
- **选择**：新增 `/dev/memory` 页面和 `/api/dev/memories` JSON 接口，统一通过 `MemoryService.list_recent()` 读取最近记录。
- **原因**：这样可以在不破坏现有低耦合记忆边界的前提下，给联调和答辩准备提供直接证据。
- **影响**：后续记忆相关验证不再只能依赖聊天表现，能直接看到具体写入内容、类型、来源和 metadata。
