# 经验沉淀

## 2026-03-24 第 1 轮迭代经验

### 有效的做法
- 将“功能实现记录”和“毕设推进记录”分层处理，更适合长期项目管理。
- OpenSpec 负责功能任务状态，explore 负责阶段过程和决策沉淀，两者结合后更容易续接。
- 当前前端阶段的每次调试都已经积累出真实问题案例，后续写论文时可以直接抽取“问题、原因、修复、验证”结构。

### 无效的做法
- 试图把所有阶段的记录都塞进单个前端专项 debug 目录，会导致主线和局部调试混在一起。
- 只在聊天里讨论“下一步做什么”，不把它回写到文件，下一轮很容易重新分析一遍。

### 可复用的策略
- 全局用一个 graduation roadmap 目录维护阶段状态。
- 每个具体实现主题用自己的 explore 子目录或 OpenSpec change workspace。
- 每轮结束时至少补三类信息：当前阶段、关键决策、经验沉淀。

### 下次要避免的坑
- 不要等到上下文很长才开始补记录，那时通常已经遗漏了关键决策细节。
- 不要把“已实现”和“已验收”混为一谈，任务状态更新时要看是否有明确证据。

## 2026-03-25 第 2 轮迭代经验

### 有效的做法
- 先用 OpenSpec 收敛本轮边界，再写后端和前端代码，可以避免“真相源还说不做后端，但代码已经做了”的分叉。
- 对于毕设 MVP，前端直连本地 HTTP 后端是比主进程桥接更稳妥的第一步，接口契约更清晰，联调成本也更低。
- 当沙箱限制本地端口绑定时，可以先用进程内方式验证 FastAPI 逻辑路径，至少把健康检查、缺密钥错误和成功返回链路跑通。
- 后端测试页和事件流先做成最小可测方案，能显著降低“后端主动控制前端”这类架构设计的验证成本。

### 无效的做法
- 在这轮就引入额外依赖和复杂编排，会拖慢“先把闭环跑起来”的节奏。
- 把“代码已落地”直接等同于“任务已验收”，会让后续论文和答辩证据不扎实。

### 可复用的策略
- 后端密钥只放在 Python 侧环境变量或 `.env`，前端只拿业务回复和错误文案，不接触供应商细节。
- 如果某个第三方依赖在当前环境缺失，但功能可以用标准库完成，优先先消除运行阻塞，再考虑后续抽象优化。
- 对于毕设这种会持续膨胀的项目，先把模块边界和可替换接口立住，比急着把每个能力都接实更重要。
- 真实开发环境一旦验证通过，要立刻把“测试路径、验证对象、结果”回写到文档，否则下一轮又会回到“代码应该已经可以了”的不确定状态。

### 下次要避免的坑
- 不要忽略仓库既有的 TypeScript 版本债务；全量类型校验失败时，要先确认是不是新改动导致，而不是盲目修自己的代码。
- 设计稿一旦把“气泡”“动作”“模式”定义为独立表现层能力，就不要再偷懒用聊天面板状态去近似替代，否则很容易在视觉和行为上偏离目标。
- 后端单文件原型一旦开始承载多个职责，就应该尽快拆层；拖到真实记忆和行为策略都接进来再拆，成本会急剧上升。

## 2026-03-26 第 3 轮迭代经验

### 有效的做法
- 在正式落地 SQLite 之前，先把 provider factory、`MemoryPolicy` 和 `MemoryStore` 边界立住，能明显降低后续替换记忆实现的成本。
- 把“常驻模型切换”和“拖拽态临时换模”分成两个状态层，能让前端模型交互规则更清楚，也更利于后续接设置页。
- 当上下文已经很长时，先把 roadmap、专项状态和 OpenSpec 同步，再做 handoff，续接质量会明显更高。

### 无效的做法
- 直接把具体存储实现写进聊天主链路，会让 MVP 看似推进更快，但会把后续切换 provider 的成本推高。
- 把 UI 新需求只记在聊天里，不回写任务和决策记录，会让下次很难分清“这只是临时想法”还是“已经确定的交互规则”。

### 可复用的策略
- 后端迭代优先顺序可以固定为：边界先行 -> 最小验证 -> 再接具体能力。
- 前端交互如果包含“常驻状态”和“临时态覆盖”，应优先显式拆成两个状态，而不是在一个布尔变量里混用。
- 每轮有实质推进后，至少同步一次全局 roadmap、专项 explore 和 OpenSpec，避免真相源分叉。

### 下次要避免的坑
- 不要在没有持久化需求确认前，就把前端本地状态直接当成最终配置方案。
- 不要等到要开新对话时才补 handoff，那时通常已经忘了哪些验证是“已完成”还是“未完成”。

## 2026-03-26 第 4 轮迭代经验

### 有效的做法
- 在回答“未来能不能接外部记忆或 agent 框架”时，先回到现有服务边界判断，而不是直接用框架名替代架构判断。
- 把当前系统定义为“可扩展底座”而不是“已经完成的 agent”，更利于后续按阶段演进，也更符合毕设 MVP 的节奏。
- 如果目标是降低耦合，应优先增加独立服务边界，例如 `ContextService`、`AgentService`、工具注册层，而不是继续膨胀单一 orchestrator。

### 无效的做法
- 只因为未来可能接 LangChain 或其他框架，就提前把现有后端改造成强依赖某个框架的结构。
- 把模型适配、记忆、感知、规划和工具调用都塞进一个服务里，会让后续替换任何一层都变贵。

### 可复用的策略
- 优先保留稳定的 `ChatOrchestrator` 主链路，再通过窄接口挂接新能力。
- 对第三方框架先做“边界级接入”而不是“全仓库级绑定”。
- 只要当前阶段目标仍是 MVP，就应把“框架能力是否酷炫”让位给“后续是否好替换、好验证、好解释”。

### 下次要避免的坑
- 不要把“未来可以演进成 agent”误写成“当前已经是 agent 框架”，否则会误导后续任务边界和答辩表述。
- 不要把扩展性目标只留在聊天里，必须同步进设计和决策文档，否则下一轮很容易回到临时性实现。

## 2026-03-26 第 5 轮迭代经验

### 有效的做法
- 做上下文感知时，先把权限边界压到“活动应用名 + 窗口标题”这种低敏感级别，再谈后续扩展，能明显降低实现和答辩解释成本。
- 先落 `ContextService` 这种服务边界，再做 provider 和提示注入，能让“失败不影响主链路”这件事更容易保证。
- 对当前仓库来说，函数级验证仍然是高性价比方案：能覆盖开关、来源提示和失败降级这些关键行为，不必被本地长驻进程状态卡住。

### 无效的做法
- 为了尽快拿到上下文，把平台调用直接写进 `ChatOrchestrator`，会立刻破坏之前刚建立好的低耦合方向。
- 一开始就把上下文设计成高敏感内容采集，会让 `Task 8` 过早背上隐私和设置负担。

### 可复用的策略
- 新能力接入顺序可以继续沿用：先抽象边界，再做最小 provider，再补控制接口，最后接入用户面向的设置页。
- 如果系统提示必须解释能力来源，就把“来源声明”做成独立 prompt note，而不是散落在 system prompt 文案里。

### 下次要避免的坑
- 不要把运行时 toggle 和持久化设置混为一谈；当前 context runtime 开关已经有了，但设置页和持久化仍属于 `Task 9`。
- 不要因为端口或本地进程状态不稳定，就放弃对服务层逻辑做验证；这类仓库更适合保留函数级验证证据。

## 2026-03-26 第 6 轮迭代经验

### 有效的做法
- 对当前桌宠这种小窗产品，先在壳层内部补一个轻量设置面板，比单独重开设置路由更适合 MVP 节奏。
- 后端如果已经提供 runtime status / toggle API，前端设置页应优先复用这些接口，而不是再发明一套平行配置协议。
- 模型形态这种纯前端展示偏好的设置，先做本地持久化就够了，不必和后端配置硬绑在一起。

### 无效的做法
- 为了“像正式产品”而在当前阶段额外引入复杂前端架构，会直接拖慢答辩主线。
- 把所有设置都做成持久化后端配置，会让简单展示偏好也承受不必要的跨层耦合。

### 可复用的策略
- 当前阶段的设置实现顺序适合固定为：先接 runtime API，再补本地展示偏好持久化，最后提供演示重置入口。
- 一键重置演示状态这种能力，在毕设项目里往往比更复杂的设置层抽象更有价值。

### 下次要避免的坑
- 不要把“有设置入口”误当成“已完成全部配置体系”；当前仍是 MVP 级最小设置面板。
- 不要忘记同步 Task 状态和 roadmap，否则很容易继续围绕已完成阶段打转。

## 2026-03-26 第 7 轮迭代经验

### 有效的做法
- 对“设置是否真的保存”这类问题，显式的保存动作往往比只做 runtime 开关更符合用户直觉。
- 在桌宠这类本地单用户应用里，先用前端本地存储承接设置快照，再在启动时回推到后端 runtime，是一条成本很低的过渡方案。
- 记忆系统一旦有了写入和召回，最好立刻补一个可视化查看页，否则排查时只能靠聊天表象猜测。

### 无效的做法
- 只做运行时切换、不提供保存语义，会让“设置页”看起来像假入口。
- 只依赖聊天回复判断记忆是否生效，会让联调非常低效，也不利于答辩讲解。

### 可复用的策略
- 对本地桌面应用，设置层可以先走“本地快照 + 启动恢复 + runtime API”三段式。
- 对可解释性要求高的能力，尽量提供一条开发态可视化页面，而不只提供 JSON 接口。

### 下次要避免的坑
- 不要把当前前端本地持久化方案误当成最终配置架构；它更像 MVP 阶段的稳定过渡方案。
- 不要忘记把新的联调入口写进文档，否则下次容易忘记 `/dev/memory` 这种高价值工具页。
