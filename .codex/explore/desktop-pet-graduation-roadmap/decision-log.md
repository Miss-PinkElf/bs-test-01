# 决策日志

## 2026-03-24 决策：将 explore 记录升级为“毕设推进工作流”
- **背景**：原先的前端专项 debug 目录更适合记录一轮前端调试，不适合长期承载整份毕业设计的阶段推进。
- **选择**：新增 `.codex/explore/desktop-pet-graduation-roadmap` 作为全局记录工作区，前端专项记录归档统一保留在 `.codex/explore/desktop-pet-ui-debug-v2`。
- **原因**：毕业设计需要按阶段留痕，既要支持后续开发续接，也要支持写论文和准备答辩；单一 debug 目录无法承载这些目标。
- **放弃的方案**：直接把单个前端专项 debug 目录改造成全局目录。
- **影响**：后续每轮主线推进先更新全局目录，再在需要时进入具体模块的 explore 或 OpenSpec workspace。

## 2026-03-24 决策：下一阶段主线切换为“简单对话 + 后端最小闭环”
- **背景**：前端展示、拖拽、缩放和联动交互已达到当前阶段目标，需要进入 MVP 更关键的可演示能力。
- **选择**：优先推进 OpenSpec 中的 `Task 5` 与 `Task 6`，先做最小对话闭环。
- **原因**：相比继续打磨前端细节，对话闭环更直接决定毕设是否具备“可运行、可演示、可解释”的价值。
- **放弃的方案**：继续延长前端细节优化，或直接跳到记忆系统。
- **影响**：后续 superspec 应围绕“前端对话入口 + Python 后端问答接口 + 前后端联调”展开。

## 2026-03-25 决策：Phase B 对话闭环优先采用本地 HTTP + FastAPI
- **背景**：这轮目标是让前端和后端尽快形成稳定、清晰、可扩展的最小通信链路。
- **选择**：前端直接通过本地 HTTP 请求 Python `FastAPI` 服务，后端统一代理上游 OpenAI 兼容接口。
- **原因**：相比 Electron 主进程桥接或 WebSocket，本地 HTTP 更容易调试、契约更清晰，也更适合后续继续接记忆和上下文接口。
- **放弃的方案**：本轮就把对话请求放进主进程 IPC，或提前接 WebSocket/流式输出。
- **影响**：前端新增独立的后端请求层，后端密钥仅保留在 Python 侧，后续阶段可继续沿用这一 API 分层。

## 2026-03-25 决策：后端上游调用改为标准库实现
- **背景**：当前环境已具备 `fastapi`、`uvicorn` 和 `python-dotenv`，但没有现成的 `httpx`。
- **选择**：本轮将上游模型调用从 `httpx` 改为标准库 `urllib`，避免为了一个最小闭环阻塞在额外依赖安装。
- **原因**：本轮重点是把骨架跑通，而不是追求库选型上的完整性；标准库足以覆盖当前一次性文本请求。
- **放弃的方案**：保留 `httpx` 并等待额外安装后再验证后端。
- **影响**：后端在当前环境中的可运行性更高；如果后续需要流式输出或更复杂的超时/重试控制，再评估是否切回专用 HTTP 客户端。

## 2026-03-25 决策：回复气泡独立于聊天面板
- **背景**：交互设计稿明确要求“对话气泡展示”属于前端表现层独立能力，而不应只是聊天面板中的最近一条消息映射。
- **选择**：assistant 回复到达后，前端立即弹出独立对话气泡；气泡与聊天面板分离，即使聊天面板关闭也会显示，并在数秒后自动隐藏。
- **原因**：这更贴近桌宠作为常驻陪伴体的表现，也更容易与后续 `bubble.show` 高层事件模型衔接。
- **放弃的方案**：继续把最近一条 assistant 消息永久映射成静态气泡。
- **影响**：前端表现层与设计稿重新对齐，后续可以更自然接入后端行为事件。

## 2026-03-25 决策：后端先重构为模块化骨架，再接真实记忆实现
- **背景**：设计稿、PRD 和原始需求都把后端定义为“大脑和中枢”，而当前单文件 `main.py` 已经无法继续承接对话、记忆、行为事件和配置的扩展。
- **选择**：先拆出 `app/api`、`app/services`、`app/memory`、`app/schemas`、`app/core` 五层结构；记忆先只保留低耦合接口与占位实现，不在这轮强接 `mem0`。
- **原因**：这样可以先把边界立住，避免聊天主链路对具体记忆方案产生强耦合，后续替换底层实现时不至于返工前端和编排层。
- **放弃的方案**：继续在单文件中追加功能，或在这轮直接把 `mem0` 强行耦进聊天流程。
- **影响**：后端后续可以继续演进出行为策略、感知服务和真实记忆实现，同时保持 Phase B 的联调链路可测。

## 2026-03-25 决策：用后端测试页 + 事件流完成最小可测推送链路
- **背景**：设计稿明确后端不仅回复用户输入，还需要具备向前端输出高层行为事件的能力。
- **选择**：新增 `/dev/control` 最小测试页和 `/api/events` 事件流，形成“后端测试页 -> 前端收到推送 -> 独立气泡展示”的最小闭环。
- **原因**：这能在真实行为策略引擎落地前，先验证事件协议、前端表现层和联调方式是否成立。
- **放弃的方案**：继续只依赖用户主动发消息，延后验证后端主动控制前端的链路。
- **影响**：后续 `bubble.show`、`mode.switch`、`move.intent` 等事件都可以沿用这一通道继续扩展。

## 2026-03-25 决策：前端新增最小 Pet Controller 承接完整高层事件
- **背景**：交互设计稿明确建议前端增加统一的 `Pet Controller`，不要让事件处理散落在多个组件里。
- **选择**：新增最小 `Pet Controller`，统一接收 `emotion.set`、`motion.play`、`bubble.show`、`mode.switch`、`move.intent` 五类事件。
- **原因**：这能让前端事件消费和后端协议保持一一对应，也为后续动作优先级、冲突仲裁和移动意图执行预留位置。
- **放弃的方案**：继续在 `App.tsx` 中只对 `bubble.show` 做特判式处理。
- **影响**：前后端接口更贴近设计稿；后续扩展真实动作、表情和窗口移动时不需要再重做事件入口。

## 2026-03-26 决策：基础记忆能力完成后，主线切向“上下文感知 + 设置能力”
- **背景**：`Task 7` 的 MVP 记忆服务已经落地，当前闭环能力已经足以支撑下一阶段的上下文和配置接入。
- **选择**：毕设主线从“简单对话闭环实施中”切换为“基础记忆收口后，优先推进轻量上下文感知与设置能力”。
- **原因**：继续在当前阶段深挖记忆复杂度的收益低于尽快补全 `Task 8`、`Task 9` 对答辩链路的支撑作用。
- **放弃的方案**：立即继续扩展更复杂的记忆结构、向量检索或长期人格能力。
- **影响**：后续开发优先级明确为 `Task 8 -> Task 9 -> Task 10`，更复杂的记忆升级留给 `Task 12` 处理。

## 2026-03-26 决策：模型交互规则显式化，Q版切换与拖拽换模分离
- **背景**：项目已同时存在正比模型和 `QQ小黑猫` 两套模型，用户要求 toolbar 上有明确的 Q版切换入口，并要求拖拽换模只在正比模型下生效。
- **选择**：前端使用明确的 `Q版` 按钮切换常驻模型类型；常驻模型为正比时，拖拽中临时切换到 `QQ小黑猫`，拖拽结束后恢复；常驻模型已是 Q版时，拖拽中不做临时换模。
- **原因**：把“常驻模型切换”和“拖拽态临时换模”拆开后，交互边界更稳定，也便于未来把模型类型接到设置页或本地配置层。
- **放弃的方案**：继续用含糊的主题占位按钮，或在任意模型形态下拖拽都强制切换。
- **影响**：后续如果要持久化模型类型，应在设置页或配置层处理，而不是继续把状态散落在拖拽逻辑里。

## 2026-03-26 决策：后续主线继续优先扩展性与低耦合，不急于把后端做成完整 agent
- **背景**：当前桌宠已经打通本地聊天闭环，并完成了低耦合的 MVP 记忆服务。用户明确希望后端后续具备更强的可扩展性，并能为外接记忆、LangChain 类框架或更强 agent 形态预留空间。
- **选择**：把当前后端定位为“可扩展的对话底座”，后续通过独立服务边界逐步引入 `ContextService`、`AgentService`、工具注册层或其他适配器，而不是把这些能力直接耦进 `ChatOrchestrator` 或 `LlmService`。
- **原因**：这样可以同时保住当前 MVP 的稳定性和未来演进空间，避免为了追求更像 agent 而把记忆、感知、工具和规划逻辑缠在一起。
- **放弃的方案**：在 `Task 8` 或 `Task 9` 阶段直接把后端重写成强依赖某个 agent 框架的大而全结构。
- **影响**：OpenSpec 设计文档需要明确“当前不是完整 agent runtime，但具备向 agent 化演进的边界”；后续实现任务应继续优先抽象边界，而不是优先堆框架特性。

## 2026-03-26 决策：Task 8 采用独立 ContextService + Windows 活动窗口 provider 的最小实现
- **背景**：当前主线要落地轻量上下文感知，但用户同时明确希望继续增强扩展性、降低耦合，而不是把平台感知逻辑直接塞进聊天主链路。
- **选择**：新增 `ContextService -> ContextProvider` 边界，当前只实现 Windows 活动窗口 provider，通过配置和 runtime toggle 控制启停；`ChatOrchestrator` 只消费可选上下文提示文本。
- **原因**：这样既能满足毕设当前阶段的最小上下文感知需求，又能为未来替换 provider、接更复杂感知策略或隐私开关留出清晰边界。
- **放弃的方案**：直接在 `ChatOrchestrator` 或聊天路由里调用 Windows API，或者一开始就接入高敏感上下文采集。
- **影响**：`Task 8` 已可视为完成；下一阶段的设置页可以直接复用 context status / toggle API，而无需重拆后端结构。

## 2026-03-26 决策：Task 9 采用轻量设置面板，而不是单独重做一套路由页
- **背景**：当前阶段目标是尽快把记忆、上下文和模型切换能力收口到用户可操作界面中，并为答辩演示提供稳定入口。
- **选择**：在现有桌宠壳层内新增轻量设置面板，直接复用 memory/context runtime API，并用本地存储持久化模型形态。
- **原因**：这样可以在不引入新前端架构的前提下完成当前验收目标，也更符合当前桌宠小窗交互形态。
- **放弃的方案**：现在就重做单独设置页面、路由或更重的前端状态体系。
- **影响**：`Task 9` 已可视为完成；下一阶段可直接转向 `Task 10` 的答辩演示脚本和材料收口。

## 2026-03-26 决策：设置页增加显式“保存当前设置”，并在下次启动自动恢复
- **背景**：仅有 runtime 开关不足以满足“设置真的被保存”的用户预期，用户明确提出需要补足设置保存语义。
- **选择**：保留当前 runtime 开关即时生效，同时新增“保存当前设置”动作，将模型形态和 memory/context 当前开关保存到前端本地存储，并在下次启动时自动回推到后端 runtime。
- **原因**：这样可以在不引入更重后端配置持久化系统的前提下，尽快满足桌宠场景下的真实使用体验。
- **放弃的方案**：继续只保留 runtime 开关、不提供显式保存语义，或当前阶段直接实现完整后端配置文件编辑体系。
- **影响**：当前 MVP 设置已具备“可保存、可恢复”的基本体验；后续若要做更完整的全局配置体系，再评估是否将这些设置迁移到后端持久配置层。

## 2026-03-26 决策：增加简单记忆查看页，直接服务联调与答辩演示
- **背景**：当前已具备 MVP 记忆写入与召回，但缺少一个像 `/dev/control` 一样的直接观察入口，难以快速判断数据库里到底写了什么。
- **选择**：新增 `/dev/memory` 和 `/api/dev/memories`，允许直接查看当前记忆存储中的最近记录。
- **原因**：这能显著降低记忆联调成本，也便于答辩前演示“系统确实写入了什么记忆”。
- **放弃的方案**：继续只靠聊天表现间接判断记忆是否写入成功。
- **影响**：后续验证记忆行为时，有了更直接、可视化、可讲解的证据入口。
