# 决策日志

## 历史决策摘要

> [#1] 2026-04-05 - 采用前后端分离的 Spring Boot + Vue Web 平台作为毕业设计落地方向，因为它最贴合开题报告且最适合答辩演示。
> [#2] 2026-04-05 - 将实现范围收敛为软件平台 MVP，不做真实硬件、机器人与数字孪生，因为这些不属于当前毕设最小交付。

## 完整记录

### [#3] 2026-04-05
- 决策：角色先采用管理员、仓库管理员、查看者三类。
- 原因：权限模型足够覆盖毕业设计常见演示场景，同时避免权限系统过度复杂。

### [#4] 2026-04-05
- 决策：预测算法先采用可解释的简单线性回归与移动平均思路。
- 原因：符合开题报告，不依赖额外机器学习框架，便于本科答辩解释。

### [#5] 2026-04-05
- 决策：一键脚本优先做“环境检查 + 启动”，而不是自动安装所有依赖。
- 原因：当前环境缺少 Maven，且网络受限，直接安装依赖的成功率不可控。

### [#6] 2026-04-06
- 决策：预测归档从单表改为 `prediction_task + prediction_result` 两层结构。
- 原因：更适合表达一次预测任务与多个未来预测点的关系，也更方便后续做预测历史列表、详情展示和归档追溯。

### [#7] 2026-04-06
- 决策：正式版 Vue 前端先引入 `Pinia + Element Plus + Axios`，并在 API 层做兼容适配，允许当前演示后端继续工作。
- 原因：这样可以先把正式技术路线和页面结构搭起来，同时避免因为后端尚未重构完成时前端被阻塞。

### [#8] 2026-04-07
- 决策：预测主线从“仅温度预测”调整为“独立多指标预测”，支持温度、湿度、二氧化碳浓度等指标按所选 `metricCode` 独立预测。
- 原因：任务书与开题报告明确环境数据是多指标管理，当前算法本质上是单序列趋势外推，通用化到多指标仍在毕设 MVP 范围内；但不扩展为多变量联合建模，避免范围失控。

### [#9] 2026-04-08
- 决策：正式业务主线从“多指标独立短期预测”进一步收口为“粮温滚动预测闭环”。
- 原因：老师最新要求明确反对仅做 24 小时短期预测，强调以前 8 个月真实数据为训练参考、预测后 2 个月每天数据、新真实数据回填验证与修正续预测，并指出核心重点在数据库设计与可追溯性。

### [#10] 2026-04-08
- 决策：温度数据不再只沿用 `sensor_data` 单值结构，而是升级为“粮温测点定义 + 原始测点记录 + 系统汇总分析 + 预测任务版本链”的分层模型；湿度与二氧化碳暂时继续保留普通单值时序。
- 原因：老师给出的 XLS 粮情报表包含大量测点层温矩阵，简单单值表难以表达；同时预测闭环需要汇总输入、真实值回填、误差验证、高温预警和修正任务链，必须引入更清晰的数据边界。

### [#11] 2026-04-08
- 决策：本期主线再次收口为“数据库优先 MVP”，暂不把“预测->修正->再预测”作为必做业务链路。
- 原因：用户最新确认老师重点是数据库、数据保存管理归档与图表展示；修正链可作为扩展功能，避免本期范围失控。

### [#12] 2026-04-08
- 决策：本期不拆独立归档表，归档继续使用 `prediction_task + prediction_result` 两层表。
- 原因：两层表已能完整表达任务归档与结果归档，额外归档表会造成重复存储与一致性负担，不利于当前进度与答辩稳定性。

### [#13] 2026-04-08
- 决策：湿度/二氧化碳保留简单单值辅线并支持“文件导入 + 手工录入”；预测页支持前端可选预测天数，图表固定展示“实际值 + 预测值”双线。
- 原因：既满足题目“数据保存管理归档”要求，又控制实现复杂度，能够快速形成可演示、可解释的数据库主链。

### [#14] 2026-04-08
- 决策：重写当前 PRD 与数据库设计真相源，并将旧版开发指导版 PRD、旧版 PRD、旧版数据库定稿、旧版接口设计归档到 `zzz-docs/Archive/`。
- 原因：当前主线已经从“修正链闭环优先”收口为“数据库优先 MVP”，若不同步重写真相源并归档旧版文件，后续恢复和开发会继续被旧文档误导。

### [#15] 2026-04-08
- 决策：粮温导入在本轮先采用“行式模板”完成数据库优先 MVP，而不是直接实现复杂矩阵式固定 XLS 模板。
- 原因：本轮目标是优先跑通“导入 -> 原始入库 -> 汇总生成 -> 按天预测 -> 归档 -> 双线图”的可演示主链；先用更简单的导入形态降低实现风险，后续再向老师更偏好的固定模板靠拢。

### [#16] 2026-04-09
- 决策：数据主线 CRUD 与温度联动重算的实施过程，统一以 `docs/superpowers/plans/2026-04-09-data-crud-and-temperature-recompute.md` 作为执行参考，并在 `.devflow/grain-platform-bootstrap/` 中显式引用。
- 原因：用户要求通过 `devflow` 持续沉淀过程；若计划只留在 `docs/` 目录而不回链到 mission 真相源，后续 handoff / resume 时容易漏掉本轮实施边界和验证目标。


### [#17] 2026-04-09
- 决策：将当前长期过程记录从 `.explore/grain-platform-bootstrap/` 复制迁移到 `.devflow/grain-platform-bootstrap/`，并新增独立的 `NEXT-SESSION-PROMPT.devflow.md`。
- 原因：用户已明确后续要切换到 `devflow` 作为长期任务主入口，同时要求保留原 `.explore/` 与原提示词不动；因此采用“复制 + 改写路径 + 保留原件”的迁移方式成本最低、恢复最稳。

### [#18] 2026-04-09
- 决策：默认开发态不再继续保留 `spring.sql.init.mode=always` 作为常态方案；后续应拆分为“日常启动保留数据”和“显式重置演示库”两种入口。
- 原因：`backend/src/main/resources/application.yml` 当前配置会在每次启动执行 `classpath:db/schema.sql`，而该脚本同时包含全量 `DROP TABLE` 与演示数据 `INSERT`。这会反复清空导入结果、CRUD 联调数据和验收样本，不利于当前“数据库优先 MVP”的稳定联调与答辩演示。

### [#19] 2026-04-09
- 决策：初始化策略收口采用“默认 `spring.sql.init.mode=never` + 独立 `scripts/reset-demo-db.ps1` 显式重置”的落地形式，而不是新增 Spring profile 来承载重置动作。
- 原因：当前本地环境以 Windows / PowerShell 为主，独立脚本比 profile 更直观，也避免把“重置数据库”和“启动应用”耦合在一次 `spring-boot:run` 中；同时这条路径更容易被后续 PowerShell 验收脚本复用。

### [#20] 2026-04-09
- 决策：仓库管理 CRUD 本轮继续沿用现有 `WarehouseDto` 作为请求/响应形状，只补当前页面真正使用的字段，并保持删除语义为“可删则硬删除、被引用则报业务错误”。
- 原因：当前 `WarehouseView.vue` 只维护 `warehouseCode`、`warehouseName`、`location`、`capacityTon`、`managerName`、`status` 六个字段，若此时扩到 `contactPhone`、`grainType`、`remark` 会扩大改动面；同时仓库已被用户、环境数据、粮温等表引用时，硬删应被拦截并返回清晰提示，而不是静默改成逻辑删除。

### [#21] 2026-04-09
- 决策：用户管理 CRUD 采用“资料 CRUD + 独立密码重置接口”的落地形式，并直接按现有 `sys_user + sys_user_role` 结构支持多角色维护；同时增加“最后一个管理员不可删除或降级”的保护规则。
- 原因：用户编辑资料与重置密码属于不同管理动作，拆开后接口语义更清晰，前端操作也更符合后台习惯；而数据库已是多角色结构，继续收缩到单角色会制造额外适配成本。管理员保护则用于避免把本地演示环境误操作到无管理员可登录的状态。
